# Phase 145.1 Plan 01: Backend Contract Upgrade Summary

## One-liner

Atomic rewrite of `GET /dashboard/today` contract to the 4-stream taxonomy (replies-needed / due-today / waiting-on-others / fyi), with server-computed `routeUrl`, deterministic `rationale`, `counts.kpi` KPI block, tz-aware scorer, and new `PATCH /tasks/:sourceType/:id/snooze` endpoint mirroring `PATCH /ai/follow-ups/:id/snooze`.

## What shipped

### DTO — `backend/src/modules/dashboard/dto/today-feed.dto.ts`

| Change | Before | After |
| --- | --- | --- |
| Stream taxonomy | `TODAY_TIERS = ['urgent', 'today', 'fyi']` | `TODAY_STREAMS = ['replies-needed', 'due-today', 'waiting-on-others', 'fyi']` |
| Item classifier field | `tier: TodayTier` | `stream: TodayStream` |
| Click-through URL | (computed frontend-side) | `routeUrl: string` (backend-computed, required) |
| Rationale | (absent) | `rationale: string | null` (deterministic 1-liner) |
| Counts keys | `urgent / today / fyi / total` | `repliesNeeded / dueToday / waitingOnOthers / fyi / total` |
| KPI block | (absent) | `kpi: { inbox, calendar, deals, tasks }` |

`TodayFeedItemDto` retains all source-linkage (`emailId`, `threadId`, `taskSourceType`, `taskSourceId`, `dealId`, `eventId`) and capability flags (`canComplete`, `canDismiss`, `canSnooze`) unchanged. `TodayFeedResponseDto.generatedAt` untouched.

### Scorer — `backend/src/modules/dashboard/services/today-scorer.service.ts`

Precedence chain rewritten to strict 4-stream order:

```
1. isAwaitingReply              -> 'replies-needed'
2. isOverdue || isToday(dueAt)  -> 'due-today'
3. isWaitingOnCounterparty      -> 'waiting-on-others'
4. otherwise                    -> 'fyi'
```

- `scoreItem(input, now, tz)` now accepts a third `tz` argument (default `'UTC'`).
- `isToday(d, now, tz)` uses `toLocaleDateString('en-CA', { timeZone: tz })` on both operands — matches `DashboardTodayService.computeWindows` to avoid drift (fixes **WR-02**).
- Dead `isHardDeadline` branch removed (fixes **WR-01**).
- Scoring helpers renamed to match streams: `scoreUrgent` → `scoreRepliesNeeded`, `scoreToday` → `scoreDueToday`, new `scoreWaiting`, `scoreFyi` kept.
- `ScoreInput` gains required fields `isAwaitingReply: boolean` and `isWaitingOnCounterparty: boolean`.

### Aggregator — `backend/src/modules/dashboard/services/dashboard-today.service.ts`

- Every normalizer (`normalizeTasks`, `normalizeFollowUps`, `normalizeDeals`, `normalizeEvents`) sets `stream` (from scorer), `routeUrl` (from item type), `rationale` (deterministic; no LLM).
- `scoreItem(..., tz)` call sites now pass the request tz through the 3rd positional arg.
- `normalizeTasks` sets `canSnooze: isFollowUp || t.sourceType === 'manual'` — enables the new snooze endpoint for manual tasks.
- `counts` block rebuilt:
  - `repliesNeeded / dueToday / waitingOnOthers / fyi / total` derived from merged items.
  - `kpi` derived from the pre-merge arrays (zero new Prisma queries):
    - `inbox    = followUpItems.length + taskItems.filter(i => i.type === 'email').length`
    - `calendar = eventItems.length`
    - `deals    = dealById.size`
    - `tasks    = taskItems.filter(i => i.type === 'task').length`
- All Prisma `where` clauses still include `tenantId` — multi-tenant guard preserved.

### Route conventions (`routeUrl`)

| Item type / source | routeUrl |
| --- | --- |
| email follow-up / task.type==='email' | `/dashboard/email/thread/{threadId ?? emailId ?? ''}` |
| task (manual/reminder/etc., type==='task') | `/dashboard/tasks` |
| deal | `/dashboard/crm/deals/{dealId}` |
| event | `/dashboard/calendar` |

### Rationale conventions (deterministic, no LLM)

| Signal | Rationale string |
| --- | --- |
| Overdue item with a dueAt | `Overdue by {N}h` (rounded, min 1) |
| Stuck deal | `No activity in 14+ days` |
| Event (always) | `Starts at HH:mm` (tz-aware) |
| Default | `null` |

### New endpoint — `PATCH /tasks/:sourceType/:id/snooze`

- **Request:** `{ "dueDate": "2026-04-19T09:00:00.000Z" }` — ISO-8601, future.
- **Response (200):** `{ "success": true, "dueDate": "<ISO>" }`.
- **Rate tier:** `safe-write`.
- **Guards:** inherits class-level `@UseGuards(TenantGuard, RolesGuard)` + `@ApiCookieAuth()`.

| `sourceType` | Backend behavior |
| --- | --- |
| `manual` | `ManualTaskService.update(tenantId, id, { dueDate })`; throws `NotFoundException` if absent via existing tenant-scoped `findOne`. |
| `follow_up` | `prisma.emailFollowUp.updateMany` with `{ id, tenantId, userId, status: in [PENDING, REMINDED] }`; resets `status=PENDING`, `remindCount=0`; throws 404 if `count===0`. |
| `reminder` | `prisma.reminder.findUnique` + tenant-equality check, then `update` with `scadenzaDatetime: dueDate`. |
| `deal_action` / `ticket` | `BadRequestException('Snooze not supported for source type: …')`. |

Past or non-ISO `dueDate`, or an unknown `sourceType`, raises `BadRequestException`.

The existing `PATCH /ai/follow-ups/:id/snooze` is untouched — both paths remain available; the today dashboard will consume `/tasks/...` for unified snooze, the follow-ups admin page still calls `/ai/...`.

## Deviations from plan

### Auto-fixed issues

**1. [Rule 1 — Bug] Reminder schema field name**
- **Found during:** Task 3, implementing `snoozeTask` reminder branch.
- **Issue:** Plan's pseudocode at `145.1-01-PLAN.md:409` and `145.1-PATTERNS.md:386` uses `data: { dueDate }` for `prisma.reminder.update`, but the Prisma `Reminder` model has no `dueDate` column — the actual field is `scadenzaDatetime` (Italian schema, carried over from legacy code).
- **Fix:** Used `data: { scadenzaDatetime: dueDate }`. The existing reminder normalizer already maps this to a unified `dueDate` externally.
- **Files modified:** `backend/src/modules/tasks/services/tasks-aggregation.service.ts`, `backend/src/modules/tasks/controllers/__tests__/tasks-snooze.spec.ts` (assertion).
- **Commit:** `2b6584bd`.

**2. [Rule 1 — Bug] LA tz test-case math**
- **Found during:** Task 1, first run of `npx jest today-scorer.service.spec.ts` (25/26 passed; only the LA case failed).
- **Issue:** Plan's behavior spec at `145.1-01-PLAN.md:164` claims `isToday('2026-04-17T05Z', '2026-04-17T07Z', 'America/Los_Angeles')` should return `true` "because both local dates = 2026-04-16". The math is wrong: April 17, 2026 in LA is UTC-7 (PDT), so `07Z` = `00:00` on `2026-04-17` local, not `16`. My correct `isToday` implementation returned `false`, rightly.
- **Fix:** Changed the test's UTC values from `(05Z, 07Z)` to `(05Z, 06Z)` — both become `22:00`/`23:00` on `2026-04-16` PDT. The spirit of the test (tz-aware isToday for a pair spanning UTC midnight in LA) is preserved.
- **Commit:** `044d5170`.
