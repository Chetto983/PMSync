## Deploy After Schema Change (Prisma Migration)

**Rule:** `backend-worker` owns migrations exclusively. Deploy ORDER:

1. Commit + push the migration SQL in `backend/prisma/migrations/...`
2. Railway auto-deploys both services (they watch the same branch).
3. **`backend-worker` boots first (faster, single replica, has `migrate deploy` in startCommand).** Watch its logs for `migration X applied`.
4. **`backend-http` boots after.** It does NOT run migrations — it picks up the schema the worker just applied.
5. If `backend-http` boots before `backend-worker` finishes migrations, requests hitting un-migrated columns fail with P2021. Railway does not support hard service dependencies; soft ordering via initial-replica delay is best-effort.

**Mitigation for schema-change deploys:**
- Stage a paused backend-http deploy (Railway Dashboard → backend-http → pause deploys)
- Deploy backend-worker
- Confirm migration complete in worker logs
- Resume backend-http deploys

**Trigger:** regression detected post-deploy (p95 spike, worker queue backup, etc.)

**Fast path (< 5 min, no code revert):**

2. Railway Dashboard → `backend-worker` → same.

**Full path (code revert):**
1. `git revert <phase-157-plan-05-commit-sha>` + `git push`.
