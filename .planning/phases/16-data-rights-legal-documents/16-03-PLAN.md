<objective>
Implement GDPR Article 17 right to erasure with a 30-day grace period: user requests deletion, system soft-deletes immediately (deactivates + invalidates sessions), and a cron job hard-deletes after 30 days.

Purpose: DATA-02 and DATA-03 require account deletion with a grace period. The current `deleteUserAccount()` does an immediate hard-delete. This plan adds a soft-delete-then-purge pattern with cancellation support.

Output: AccountDeletionService (soft-delete, cancel, purge), DataDeletionController (request, status, cancel endpoints), purge cron in DataCleanupService.
</objective>

**1. Create `dto/data-deletion.dto.ts`:**
- `DeletionStatusDto`: `{ status: 'ACTIVE' | 'SCHEDULED' | 'CANCELLED', deletedAt?: Date, purgeDate?: Date, daysRemaining?: number }`
- `DeletionResponseDto`: `{ status: string, purgeDate: Date, message: string }`

**2. Create `services/account-deletion.service.ts`:**

Inject PrismaService, AuditService (via @Optional() @Inject()), Logger.

**`requestDeletion(userId, tenantId)`:**
- Check if user is already soft-deleted (has deletedAt set). If so, return existing deletion info.
- Run in `prisma.$transaction`:
  - Update user: `{ deletedAt: new Date(), isActive: false }`
  - Delete all sessions: `prisma.session.deleteMany({ where: { userId } })`
- Calculate purgeDate: `new Date(Date.now() + 30 * 24 * 60 * 60 * 1000)` (30 days from now)
- Log audit event: `this.auditService?.logAudit(tenantId, userId, 'DELETION_REQUESTED', 'User', userId)`
- Return `{ status: 'SCHEDULED', purgeDate, message: 'Account scheduled for deletion. You can cancel within 30 days.' }`

**`cancelDeletion(userId, tenantId)`:**
- Verify user has deletedAt set. If not, throw BadRequestException('No pending deletion request')
- Verify still within 30-day grace period. If past 30 days, throw GoneException('Grace period expired, deletion cannot be cancelled')
- Update user: `{ deletedAt: null, isActive: true }`
- Log audit: `this.auditService?.logAudit(tenantId, userId, 'DELETION_CANCELLED', 'User', userId)`
- Return `{ status: 'CANCELLED', message: 'Account deletion cancelled. Your account has been reactivated.' }`

**`getDeletionStatus(userId)`:**
- Query user for deletedAt and isActive
- If deletedAt is null: return `{ status: 'ACTIVE' }`
- If deletedAt is set: calculate daysRemaining = 30 - daysSince(deletedAt). Return `{ status: 'SCHEDULED', deletedAt, purgeDate, daysRemaining }`

**`purgeExpiredDeletions()`:**
- This is the cron-called method.
- Calculate cutoff: `new Date(Date.now() - 30 * 24 * 60 * 60 * 1000)` (30 days ago)
- Query: `prisma.user.findMany({ where: { deletedAt: { not: null, lt: cutoff } }, select: { id: true, tenantId: true } })`
- For each user found: call `this.hardDeleteUser(user.id, user.tenantId)`
- Log count of purged users

**`hardDeleteUser(userId, tenantId)`:**
- Log audit BEFORE delete (audit record will be cascade-deleted too, but log to console): `this.logger.warn(\`Hard-deleting user ${userId} from tenant ${tenantId}\`)`
- Call `prisma.user.delete({ where: { id: userId } })` -- Prisma cascades will handle all related records (emails, contacts, calendar, etc.)
- This intentionally uses the Prisma cascade rather than manually deleting each relation. The schema already has `onDelete: Cascade` on all User relations.
- Wrap in try/catch: on P2025 (record not found), log warning and continue (user may have been manually deleted already).

IMPORTANT: Do NOT modify the existing `UsersService.deleteUserAccount()`. Leave it as-is for backward compatibility. The new AccountDeletionService provides the grace-period flow. If later the old direct-delete path needs to be removed, that's a separate task.
