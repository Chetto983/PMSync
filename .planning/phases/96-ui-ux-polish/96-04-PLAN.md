  <action>
Audit all 9 non-email/calendar/contacts pages for mobile responsiveness at 375px width. (Email, calendar, contacts, and chat already have responsive layouts per research.)

For each page, look for these mobile-breaking patterns and fix them:

1. **Fixed-width elements:** Replace fixed pixel widths with responsive alternatives using `{ width: { xs: '100%', md: 400 } }` or percentage widths.

2. **Horizontal overflow from tables:** Admin users and admin organizations likely have tables. Hide non-essential columns at mobile: `{ display: { xs: 'none', md: 'table-cell' } }` on less-important columns (e.g., created date, role). Keep essential columns (name, email/status, actions).

3. **Side-by-side layouts not stacking:** Settings page with left tab list + right content should stack vertically on mobile. Use `{ flexDirection: { xs: 'column', md: 'row' } }` or switch from vertical Tabs to horizontal Tabs on mobile.

4. **Text overflow:** Add `overflow: 'hidden'`, `textOverflow: 'ellipsis'`, `whiteSpace: 'nowrap'` to long text elements (email subjects, user names, descriptions).

5. **Padding too wide:** Ensure content padding is `{ px: { xs: 2, sm: 3, md: 4 } }` (16px/24px/32px).

6. **Dashboard grid:** Ensure widget grid is single column on mobile: `{ gridTemplateColumns: { xs: '1fr', md: 'repeat(2, 1fr)', lg: 'repeat(3, 1fr)' } }`.

7. **Kanban layouts (tasks/reminders):** On mobile, stack kanban columns vertically or switch to list view. Use `{ flexDirection: { xs: 'column', md: 'row' } }` on the kanban container.

8. **Profile form:** Forms typically work well on mobile, but check for any fixed-width inputs or side-by-side fields that need stacking.

9. **Analytics charts:** Ensure chart containers have `width: '100%'` and a reasonable min-height. The 2x2 grid should become 1-column on mobile.

For each file, use `useMediaQuery(theme.breakpoints.down('md'))` for mobile detection, consistent with existing email/chat patterns.

IMPORTANT: Only fix issues you can identify from reading the code. Don't add responsive styles to elements that are already responsive or don't need them. Read each file fully before making changes.

  <action>
Three sub-tasks:

**A. Dark mode audit:**
Search all files modified in Plans 02 and 03 for hardcoded colors. Look for patterns:
- `bgcolor: '#fff'` or `bgcolor: 'white'` -- replace with `bgcolor: 'background.paper'`
- `color: '#000'` or `color: 'black'` -- replace with `color: 'text.primary'`
- `borderColor: '#e0e0e0'` or similar -- replace with `borderColor: 'divider'`
- `backgroundColor: 'rgb(...)` -- replace with theme tokens
- Any `sx={{ ... }}` with hardcoded hex values that should be theme-aware

Run: `grep -rn "bgcolor.*#\|color.*#[0-9a-fA-F]\{3,6\}\|background.*#" frontend/pages/dashboard/ frontend/components/dashboard/ frontend/components/productivity/ frontend/components/admin/ frontend/components/analytics/ frontend/components/settings/` to find candidates.

Fix any hardcoded colors that would break in dark mode. Leave intentional semantic colors (like the empty state icon colors which use alpha).

**B. Keyboard navigation audit:**
Search for custom clickable elements that lack keyboard support:
`grep -rn "onClick.*Box\|onClick.*div\|onClick.*span" frontend/pages/dashboard/ frontend/components/dashboard/ frontend/components/productivity/ frontend/components/admin/`

For any `Box`/`div`/`span` with `onClick` that is NOT inside an MUI `Button`/`IconButton`/`ListItemButton`:
1. Add `role="button"`
2. Add `tabIndex={0}`
3. Add `onKeyDown={(e) => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); onClickHandler(); } }}`

MUI components (Button, IconButton, ListItemButton, Tab, TextField, etc.) already have keyboard support -- skip those.

**C. i18n gap closure:**
1. Run `npx tsx frontend/scripts/i18n-audit.ts` (from Plan 01) to get list of missing keys
2. For every key missing in `it.ts`, add the Italian translation
3. For every key missing in `en.ts`, add the English translation
4. Update `frontend/locales/index.ts` type definitions if new key paths were added
5. Grep `.tsx` files for remaining hardcoded English strings: search for patterns like `title="[A-Z]` or `>[A-Z][a-z]+ [a-z]` that look like hardcoded user-visible text (exclude `aria-label` values which are English-acceptable)
6. Replace any remaining hardcoded strings with translation keys (add to both en.ts and it.ts)
7. Re-run `npx tsx frontend/scripts/i18n-audit.ts` -- must exit 0

IMPORTANT: The i18n audit may reveal a large number of gaps from pre-existing code. Focus on gaps in pages touched by Phase 96 (the 16 protected pages). Pre-existing gaps in untouched files should be noted but are lower priority.
