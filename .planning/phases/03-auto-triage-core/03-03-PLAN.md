Build implicit signal tracking service and wire learning feedback into triage recalculation.

Purpose: TRIAGE-03 requires learning from user actions. Currently there is zero tracking of implicit signals (email opens, replies, archives, flags). The existing AgentLearningProfile handles HITL actions (approve/reject proposed AI actions), but triage learning needs to observe passive user behavior and update sender importance weights. Create a new file `backend/src/modules/ai/services/triage-learning.service.ts` (max 300 lines).

This service tracks implicit user behavior signals and aggregates per-sender scores. It does NOT create a new DB table — it stores aggregated sender behavior scores in the existing Contact.metadata JSON field as a `triageBehavior` key. This is acceptable because we WRITE to metadata (not query by it) — reads use the Contact record itself.

**Interface:**

```typescript
export interface TriageSignal {
  tenantId: string;
  userId: string;
  emailId: string;
  senderEmail: string;
  signalType: 'reply' | 'archive' | 'delete' | 'flag' | 'forward';
  responseTimeMs?: number; // Time between email receivedAt and action
}

export interface SenderBehaviorScore {
  replyRate: number;       // 0.0-1.0 — fraction of emails replied to
  avgResponseTimeMs: number;
  archiveWithoutReplyRate: number; // 0.0-1.0
  flagRate: number;        // 0.0-1.0
  totalSignals: number;
  lastUpdated: string;     // ISO date
}
```

**Class: TriageLearningService**

Injectable NestJS service with:

1. `private signalBuffer: Map<string, TriageSignal[]>` — In-memory buffer keyed by `${tenantId}:${senderEmail}`. Prevents per-action DB writes.

2. `recordSignal(signal: TriageSignal): void` — Adds signal to buffer. When buffer for a sender reaches 5 signals OR on a 5-minute interval (use `setInterval` in `onModuleInit`, clear in `onModuleDestroy`), calls `flushSenderSignals()`.

3. `private async flushSenderSignals(key: string, signals: TriageSignal[]): Promise<void>` — Computes aggregated SenderBehaviorScore from signals:
   - replyRate = count(reply) / totalSignals
   - avgResponseTimeMs = average of responseTimeMs where defined
   - archiveWithoutReplyRate = count(archive) / totalSignals
   - flagRate = count(flag) / totalSignals
   Then finds the Contact by senderEmail (using emails JSON path), and updates Contact.metadata by merging the new `triageBehavior` score with existing metadata:
   ```typescript
   const existing = (contact.metadata as Record<string, unknown>) || {};
   const prevBehavior = existing.triageBehavior as SenderBehaviorScore | undefined;
   // EMA blend: 70% existing + 30% new (if previous exists)
   const blended = prevBehavior
     ? blendScores(prevBehavior, newScore, 0.7)
     : newScore;
   await this.prisma.contact.update({
     where: { id_tenantId: { id: contact.id, tenantId } },
     data: { metadata: { ...existing, triageBehavior: blended } },
   });
   ```

4. `async getSenderBehavior(tenantId: string, senderEmail: string): Promise<SenderBehaviorScore | null>` — Reads Contact.metadata.triageBehavior for the sender. Used by AttentionScoreService during recalculation.

5. `async getTopSenderScores(tenantId: string, limit: number): Promise<Array<{ senderEmail: string; score: SenderBehaviorScore }>>` — Returns senders with the most signals, for the recalculation job.

6. Implement `OnModuleInit` (start flush interval) and `OnModuleDestroy` (flush all remaining, clear interval).

Helper: `blendScores(prev: SenderBehaviorScore, curr: SenderBehaviorScore, prevWeight: number)` — EMA blend of two scores.
