  <action>
Run the validation script against Gmail first (most likely to have data):

```bash
node scripts/validate-attachments-search.mjs --provider=gmail
```

Analyze the output. For each FAIL result:

1. **Identify root cause**: Is it a script bug (wrong response envelope path, wrong assertion) or a backend bug (incorrect logic, missing data)?

2. **Script bugs**: Fix the validation script's response parsing. Common issues from RESEARCH.md:
   - Attachment endpoint path must be `/api/v1/email/attachments/` (singular `email`, not `emails`) -- 404 means wrong path
   - Response envelope: try `res?.data ?? res` for metadata, stats, search responses
   - Search response shape: `searchData?.emails ?? searchData ?? []`
   - Stats may be wrapped in `{ data: ... }` envelope
   - Download endpoint returns binary, NOT JSON -- must use `context.request.get()` not `apiGet()`

3. **Backend bugs**: Fix in the backend source. Potential issues:
   - AttachmentsController missing tenant isolation in download query
   - S3 signed URL expired or MinIO unreachable (check error message)
   - Stats `getStats()` missing a provider filter
   - Search `searchEmails()` not handling empty query param
   - After ANY backend edit, run `cd backend && npx tsc --noEmit` to verify types

4. Re-run after each fix: `node scripts/validate-attachments-search.mjs --provider=gmail`

5. Once Gmail passes, run for other providers if available:
   ```bash
   node scripts/validate-attachments-search.mjs --provider=outlook
   node scripts/validate-attachments-search.mjs --provider=imap
   ```

6. Final full run: `node scripts/validate-attachments-search.mjs`

Bug fix scope: Only fix what the validation reveals. Do not refactor, do not add features. If a bug requires > 50 lines of change, document it and ask before proceeding.

Special attention for attachment validation:
- If no emails with attachments exist for a provider, the script should SKIP (not FAIL). This is expected.
- The on-demand fetch (READ-07) cannot be forced -- it depends on whether the attachment is already cached in S3. The validation checks both paths via the metadata `isInS3` field.
- If the download returns a non-200 status, check if S3/MinIO is reachable from the backend.
