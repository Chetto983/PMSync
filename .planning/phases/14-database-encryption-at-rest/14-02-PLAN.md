  <action>
Create `backend/src/prisma/encryption/field-encryption.extension.ts` (~120 lines):

The extension intercepts Prisma `$allModels.$allOperations` to encrypt on write and decrypt on read.

```typescript
export function createFieldEncryptionExtension(
  getKeyForTenant: (tenantId: string) => Buffer,
  getDecryptionKeys: (tenantId: string) => Buffer[],
)
```

**Write path** (create, update, upsert, createMany, updateMany):
1. Check if model has entries in `ENCRYPTED_FIELDS` config. If not, pass through.
2. Extract `tenantId` from `args.data.tenantId` or `args.where.tenantId` or nested patterns.
3. If no tenantId found, pass through (safety — don't encrypt without tenant context).
4. For each configured field on this model: if field exists in `args.data` and is a non-null string, replace with `encryptFieldValue(value, key)`.
5. Handle nested `data` in `upsert` (both `create` and `update` blocks).
6. For `createMany`: iterate `args.data` array, encrypt each record's fields.

**Read path** (findFirst, findUnique, findMany, and results from write ops):
1. After `query(args)` returns, check result.
2. If result is an array, decrypt each element. If single object, decrypt it.
3. For each configured field: if field value is a string, call `decryptFieldValue(value, decryptionKeys)`.
4. Plaintext values (no `enc:` prefix) pass through unchanged — critical for migration coexistence.

**tenantId extraction helper** (~20 lines):
- Check `args.data?.tenantId`, `args.where?.tenantId`, `args.where?.id_tenantId?.tenantId` (composite PK pattern).
- For `createMany`, extract from first record in `args.data` array.
- Return `string | null`.

**CRITICAL constraints:**
- Do NOT modify `args.where` — encrypted fields cannot be searched by value (hash fields handle that separately).
- Do NOT encrypt null/undefined values.
- Do NOT encrypt non-string values (skip boolean, number, Date, Json fields).
- Handle the case where `args.data` may be undefined (e.g., `findMany` with only `where`).
- Use `Prisma.defineExtension()` for type-safe extension definition.

The function is pure (no NestJS DI) — it accepts key-getter functions as parameters. This makes it testable without NestJS.

Modify `backend/src/prisma/prisma.service.ts`:

1. Import `TenantKeyService` and `createFieldEncryptionExtension`.
2. In the constructor, AFTER `super({ adapter: createPrismaAdapter() })`:
   - Instantiate `TenantKeyService` (it uses `getConfiguration()` internally, no DI needed).
   - Check if `fieldEncryption.masterKey` is configured (non-empty). If NOT configured, skip extension (encryption is opt-in).
   - If configured, call `this.$extends(createFieldEncryptionExtension(...))` to attach the extension.
3. The `$extends()` call returns a new client instance. Prisma 7 handles this — the extended client replaces the base.

**IMPORTANT Prisma 7 $extends behavior:**
Prisma's `$extends()` returns a NEW client, it doesn't mutate the existing one. So you need:
```typescript
const extendedClient = this.$extends(createFieldEncryptionExtension(
  (tenantId) => tenantKeyService.getCurrentKey(tenantId),
  (tenantId) => tenantKeyService.getDecryptionKeys(tenantId),
));
// Copy extended methods back (Prisma extension pattern)
Object.assign(this, extendedClient);
```

Actually, the cleaner pattern for NestJS + Prisma 7 is to use a factory approach. Modify the service to conditionally extend:

```typescript
constructor() {
  super({ adapter: createPrismaAdapter() });

  const config = getConfiguration();
  if (config.fieldEncryption.masterKey) {
    const tenantKeyService = new TenantKeyService();
    // Note: $extends returns new instance, but since PrismaService extends PrismaClient,
    // we need to store the extended reference. The safest approach is to apply
    // the extension in onModuleInit and store it, or use the NestJS provider factory pattern.
  }
}
```

ALTERNATIVE (simpler, recommended): Instead of extending PrismaService itself, create a factory provider in PrismaModule that produces the extended client. Read PrismaService source carefully before deciding — if `$extends()` doesn't work well with class inheritance, use the factory approach:

```typescript
// prisma.module.ts
@Global()
@Module({
  providers: [
    {
      provide: PrismaService,
      useFactory: () => {
        const service = new PrismaService();
        // Extension applied inside PrismaService constructor
        return service;
      },
    },
  ],
  exports: [PrismaService],
})
```

Whichever approach compiles and works — verify with `tsc` first. The goal: when FIELD_ENCRYPTION_MASTER_KEY is set, all Prisma operations go through the encryption extension. When not set, Prisma works exactly as before (zero behavior change).

Do NOT change PrismaModule exports — `PrismaService` must remain the exported token.
