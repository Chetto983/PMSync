Create `backend/src/common/services/tenant-key.service.ts` — a NestJS injectable service:

1. Import `hkdfSync` from Node.js `crypto` (built-in, no new deps).
2. Read master key from config: `this.config.fieldEncryption.masterKey` (base64-encoded, min 32 bytes decoded).
3. Read old master keys from config: `this.config.fieldEncryption.oldMasterKeys` (comma-separated base64 strings for rotation).
4. `deriveKey(masterKey: Buffer, tenantId: string): Buffer` — uses `hkdfSync('sha256', masterKey, tenantId, 'mailagent-field-enc-v1', 32)`.
5. `getCurrentKey(tenantId: string): Buffer` — derives from current master key, caches in `Map<string, Buffer>`.
6. `getDecryptionKeys(tenantId: string): Buffer[]` — returns `[currentKey, ...oldDerivedKeys]` for rotation fallback.
7. `clearCache(): void` — clears the in-memory key cache (call on key rotation).
8. Constructor validates master key length (>= 32 bytes decoded). Throws on invalid.

Use the existing `getConfiguration()` pattern from `crypto.service.ts` — do NOT inject ConfigService. Import `getConfiguration` from `../../config/configuration`.

Register env vars:
- In `env.validation.ts`: Add `FIELD_ENCRYPTION_MASTER_KEY` (string, @IsOptional) and `FIELD_ENCRYPTION_OLD_KEYS` (string, @IsOptional).

  ```
  fieldEncryption: {
    masterKey: string;
    oldMasterKeys: string;
  }
  ```

  Map from `process.env.FIELD_ENCRYPTION_MASTER_KEY || ''` and `process.env.FIELD_ENCRYPTION_OLD_KEYS || ''`.
  Add security validation: in production, if masterKey is set but < 32 chars, throw. Do NOT require it (encryption is opt-in until migration).

IMPORTANT: Keep the service under 100 lines. Follow the exact pattern from CryptoService (Logger, constructor validation, getConfiguration).

  <action>
Create `backend/src/prisma/encryption/` directory with two files:

**field-encryption.utils.ts** (~80 lines):
1. `ENCRYPTION_PREFIX = 'enc:'` — marker to detect encrypted vs plaintext values.
2. `encryptFieldValue(plaintext: string, key: Buffer): string` — AES-256-GCM encrypt, returns `enc:` + base64(iv + ciphertext + authTag). IV = 12 bytes random, authTag = 16 bytes.
3. `decryptFieldValue(stored: string, keys: Buffer[]): string` — if not `enc:` prefixed, return as-is (plaintext pass-through for migration). Strip prefix, try each key in order. Return decrypted string. Throw if ALL keys fail.
4. `isEncrypted(value: string): boolean` — checks `enc:` prefix.
5. `hashForSearch(value: string, tenantId: string, salt: string): string` — SHA-256 hash of `${salt}:${tenantId}:${value.toLowerCase().trim()}`. Returns hex string. Used for exact-match search on encrypted fields.

Use only Node.js built-in `crypto` module. No external dependencies.

**encryption.config.ts** (~50 lines):
Define the encrypted fields configuration:

```typescript
export interface EncryptedFieldConfig {
  field: string;       // The model field name
  hashField: string | null; // Companion hash field for exact-match search (null = no search)
}

export const ENCRYPTED_FIELDS: Record<string, EncryptedFieldConfig[]> = {
  Email: [
    { field: 'bodyText', hashField: null },
    { field: 'bodyHtml', hashField: null },
    { field: 'snippet', hashField: null },
  ],
  // Tier 2 fields (from, subject, displayName) NOT encrypted yet.
  // They use contains+insensitive queries in 17+ locations.
  // Encrypting them requires search infrastructure redesign (deferred).
};
```

CRITICAL: Only Tier 1 fields (bodyText, bodyHtml, snippet) are configured. These are:
- NOT used in `contains` queries
- NOT used in trigram GIN indexes
- ONLY read for display or embedding content (embedding pipeline sanitizes PII separately via Phase 13)

Do NOT add Contact, User, or ProviderConfig fields yet. ProviderConfig tokens are already encrypted by CryptoService (AES-256-CBC). Contact Json fields (emails, phoneNumbers) require serialize-then-encrypt which is complex. These are Tier 2.

Export `getEncryptedFieldsForModel(modelName: string): EncryptedFieldConfig[]` helper function.
