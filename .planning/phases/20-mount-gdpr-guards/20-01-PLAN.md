# Plan 20-01: Wire GDPR Guards into Runtime Enforcement

**Phase:** 20 — Mount GDPR Guards
**Requirements:** CONS-02, LEGAL-01, LEGAL-02
**Depends on:** Phase 15 (ConsentGuard), Phase 16 (LegalAcceptanceGuard)

## Problem Statement

ConsentGuard and LegalAcceptanceGuard were built in Phases 15-16 and have passing unit tests, but neither is mounted in the application runtime. The guards are exported from ComplianceModule but never registered as APP_GUARD and never applied via @UseGuards on any controller. Users can bypass legal acceptance and call AI endpoints without consent.

## Approach

Register both guards as global APP_GUARD providers in `app.module.ts`, then decorate exempt routes with `@SkipLegalCheck()` and AI processing routes with `@RequiresConsent('ai_email_processing')`.

### Key Design Decisions

1. **LegalAcceptanceGuard as APP_GUARD** — enforces globally on all authenticated routes, exempted with `@SkipLegalCheck()`
2. **ConsentGuard as APP_GUARD** — runs globally but is a no-op unless handler has `@RequiresConsent()` decorator (existing behavior)
3. **LegalAcceptanceGuard graceful skip on unauthenticated routes** — return `true` when `request.user` is absent (unauthenticated routes don't have a user identity to check against). Without this fix, every unauthenticated route (health, webhooks, auth) would throw ForbiddenException
4. **New `ai_email_processing` umbrella consent feature** — covers all VoltAgent chat/stream AI processing endpoints. Individual per-tool consent can be added later as a refinement
5. **`@SkipLegalCheck()` at class level** on compliance controllers — all compliance endpoints must remain accessible before legal acceptance (users need to check status and accept documents)

## Tasks

### Task 1: Fix LegalAcceptanceGuard for unauthenticated routes

**File:** `backend/src/modules/compliance/guards/legal-acceptance.guard.ts`

**Change:** After the `@SkipLegalCheck` check, add an early return when `request.user` is absent. This handles unauthenticated routes (health, webhooks, auth) that don't have JwtAuthGuard and therefore have no user on the request.

**Before:**
```ts
const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
const userId = request.user?.userId ?? request.user?.id;
const tenantId = request.user?.tenantId;

if (!userId || !tenantId) {
  throw new ForbiddenException('Authentication required for legal acceptance check');
}
```

**After:**
```ts
const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
const userId = request.user?.userId ?? request.user?.id;
const tenantId = request.user?.tenantId;

// Unauthenticated routes (no JwtAuthGuard) have no user — skip legal check
if (!request.user) {
  return true;
}

if (!userId || !tenantId) {
  throw new ForbiddenException('Authentication required for legal acceptance check');
}
```

**Rationale:** When registered as APP_GUARD, the guard runs on ALL routes including unauthenticated ones (health, webhooks, auth). Without a user identity, there's nothing to check. JwtAuthGuard already protects authenticated routes — if a user reaches the legal guard with a JWT, they WILL have userId/tenantId.

**Verification:** Existing unit tests still pass. New test for unauthenticated request returns true.

### Task 2: Register both guards as APP_GUARD in app.module.ts

**File:** `backend/src/modules/app.module.ts`

**Changes:**
1. Import `LegalAcceptanceGuard` and `ConsentGuard` from `ComplianceModule`
2. Add two new `APP_GUARD` providers after the existing `ThrottlerGuard`

**Order matters:** ThrottlerGuard → LegalAcceptanceGuard → ConsentGuard
- ThrottlerGuard runs first (rate limiting before any business logic)
- LegalAcceptanceGuard runs second (block users without legal acceptance)
- ConsentGuard runs third (block specific features without consent)

**Code to add in providers array:**
```ts
// LEGAL-01/02: Block users who haven't accepted TOS/Privacy Policy
{
  provide: APP_GUARD,
  useClass: LegalAcceptanceGuard,
},
// CONS-02: Block AI processing without consent
{
  provide: APP_GUARD,
  useClass: ConsentGuard,
},
```

**Import addition:**
```ts
import { LegalAcceptanceGuard } from './modules/compliance/guards/legal-acceptance.guard';
import { ConsentGuard } from './modules/compliance/guards/consent.guard';
```

**Note:** Both guards are already exported from ComplianceModule which is imported in app.module.ts. However, APP_GUARD registration requires direct class reference — NestJS creates a new instance for each APP_GUARD. Since both guards depend on services from ComplianceModule (ConsentEnforcementService, LegalAcceptanceService), and ComplianceModule exports these services, the DI will resolve correctly.

**Wait — potential issue:** APP_GUARD instances are created by the root module, not by ComplianceModule. The guards' dependencies (ConsentEnforcementService, LegalAcceptanceService, Reflector) must be available in the root module's DI scope. Since ComplianceModule exports these services and is imported in AppModule, this should work. Reflector is globally available from NestJS core.

**Verification:** `npm run build` succeeds. App starts without DI errors.

### Task 3: Add @SkipLegalCheck on exempt controllers

All controllers that must remain accessible BEFORE legal acceptance:

| Controller | Route Prefix | Reason |
|---|---|---|
| `LegalController` | `compliance/legal` | User must be able to check status and accept documents |
| `ConsentController` | `compliance/consent` | User must be able to manage consent before legal acceptance doesn't gate consent UI |
| `DataExportController` | `compliance/data-export` | GDPR data rights must remain accessible |
| `DataDeletionController` | `compliance/data-deletion` | GDPR right to erasure must remain accessible |
| `GdprController` | `compliance/gdpr` | GDPR status endpoint must remain accessible |

**Pattern:** Add `@SkipLegalCheck()` at the class level on each controller.

```ts
import { SkipLegalCheck } from '../decorators/skip-legal-check.decorator';

@SkipLegalCheck()
@Controller('compliance/legal')
export class LegalController { ... }
```

**Controllers NOT needing @SkipLegalCheck (and why):**
- `HealthController` — no auth, guard skips via Task 1 fix (no user)
- `AuthController` — no auth on most routes, guard skips via Task 1 fix
- `OAuthCallbackController` — no auth, guard skips via Task 1 fix
- `MfaController` — no auth on most routes, guard skips via Task 1 fix
- `WebhookController` — no auth, guard skips via Task 1 fix
- All other webhook controllers — no auth, guard skips via Task 1 fix
- `AiHealthController` — no auth (`ai/health`), guard skips via Task 1 fix

**Verification:** Compliance endpoints remain accessible for users who haven't accepted legal documents.

**Step 4b: Add @RequiresConsent to VoltAgent chat endpoints**

**File:** `backend/src/modules/ai/voltagent/voltagent.controller.ts`

Add `@RequiresConsent('ai_email_processing')` on the two main chat handlers:

```ts
import { RequiresConsent } from '../../compliance/decorators/requires-consent.decorator';

@Post('chat')
@RequiresConsent('ai_email_processing')
@RequiresQuota('ai')
async chat(...) { ... }

@Post('chat/stream/v3')
@RequiresConsent('ai_email_processing')
@RequiresQuota('ai')
async streamChatV3(...) { ... }
```

**NOT adding @RequiresConsent to:**
- `GET suggested-prompts` — read-only, no AI processing
- `GET/POST actions/*` — approval workflow, not new AI processing
- `GET stats/*` — telemetry, no data processing
- `POST cache/*` — cache management, no AI processing
- `GET briefing` — user explicitly requests this (consent checked at chat level)
- `GET deadlines/*` — stubs returning empty data

**Step 4c: Add @RequiresConsent to AI controller chat/analysis endpoints**

**File:** `backend/src/modules/ai/controllers/ai.controller.ts`

The AiController has endpoints for email summarization, smart replies, categorization, etc. These all process email content with AI. Add `@RequiresConsent('ai_email_processing')` on the class level since ALL endpoints in this controller use AI processing.

```ts
import { RequiresConsent } from '../../compliance/decorators/requires-consent.decorator';
```

Individual handlers that process content should get the decorator. Since the ConsentGuard checks at handler level, we add it to each handler rather than class level.

Specific handlers: `chat`, `summarize`, `smartReply`, `categorize`, `sentiment`, `priority`, `compose`, `analyzeEmail`.

**Step 4d: Add translations for new consent feature**

**Files:** `frontend/locales/en.ts`, `frontend/locales/it.ts`

Add label and description for `ai_email_processing` in the consent settings UI strings. The frontend reads consent feature metadata from the backend, but translations for display are in locales.

**Verification:** Calling `POST /api/v1/voltagent/chat` without `ai_email_processing` consent returns 403 Forbidden.

### Task 5: Integration test

**File:** `backend/src/modules/compliance/__tests__/gdpr-guards-integration.spec.ts`

Unit tests covering:

1. **LegalAcceptanceGuard as APP_GUARD:**
   - Unauthenticated request → returns true (skips)
   - Authenticated user with legal acceptance → returns true
   - Authenticated user WITHOUT legal acceptance → throws ForbiddenException
   - Route with @SkipLegalCheck → returns true regardless of acceptance

2. **ConsentGuard as APP_GUARD:**
   - Handler without @RequiresConsent → returns true
   - Handler with @RequiresConsent + user has consent → returns true
   - Handler with @RequiresConsent + user lacks consent → throws ForbiddenException

3. **Guard ordering:**
   - LegalAcceptanceGuard runs before ConsentGuard (a user blocked by legal should not even reach consent check)

**Test pattern:** Follow existing `consent.guard.spec.ts` pattern with mock ExecutionContext and mock services. Pure Jest mocks (no NestJS TestingModule).
