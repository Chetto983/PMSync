**Follow Playwright skill golden rules:**
1. Use `getByRole()` over CSS selectors
2. Never use `page.waitForTimeout()` -- use `expect(locator).toBeVisible()` or `page.waitForURL()`
3. Web-first assertions (auto-retry)
4. Use `baseURL` from config (no hardcoded URLs)
5. One behavior per test

**Import pattern:**
```typescript
import { test, expect } from './fixtures';
```

Use the `authedPage` fixture from fixtures.ts for authenticated page access.

**Test describe block: "AI Chat E2E"**

**beforeEach setup (for all tests):**
- Mock `GET **/api/v1/ai/chat/conversations` to return `[]` (empty conversation list)
- Mock any other required API endpoints that the chat page fetches on load (check by navigating to /dashboard/ai with Playwright trace to see what APIs are called)

**Test 1: "sends message and receives streaming response"**
- Mock `POST **/api/v1/ai/chat` with Data Stream format response containing text deltas:
  ```
  0:"Hello "\n
  0:"from the AI assistant!"\n
  d:{"finishReason":"stop","usage":{"inputTokens":10,"outputTokens":5}}\n
  ```
- Navigate to `/dashboard/ai`
- Find the composer textbox (likely `getByRole('textbox')` or a more specific role)
- Fill with "Hello"
- Press Enter (or click send button)
- Assert: `expect(page.getByText('Hello from the AI assistant!')).toBeVisible()`

**Test 2: "displays tool result card for search_emails"**
- Mock `POST **/api/v1/ai/chat` with a tool call + tool result + text response:
  ```
  9:{"toolCallId":"call_1","toolName":"search_emails","args":{"query":"meeting"}}\n
  a:{"toolCallId":"call_1","result":{"success":true,"data":[{"id":"e1","subject":"Team Meeting","from":"john@example.com","snippet":"Weekly sync","receivedAt":"2026-03-01T10:00:00Z","isRead":true,"isStarred":false,"aiPriority":5,"aiSentiment":"neutral","aiLabels":["work"]}],"searchType":"text"}}\n
  0:"I found 1 email about meetings."\n
  d:{"finishReason":"stop","usage":{"inputTokens":20,"outputTokens":10}}\n
  ```
- Navigate to `/dashboard/ai`, send a message
- Assert: tool result card is visible (look for the email subject "Team Meeting" in the rendered tool UI, or check for a tool card container element)
- Assert: text response "I found 1 email about meetings." is visible

**Test 3: "shows HITL approval card for destructive action"**
- Mock `POST **/api/v1/ai/chat` with a response that includes a pending HITL action
- Mock `GET **/api/v1/ai/actions/pending` to return a pending action:
  ```json
  [{"id":"act_1","toolName":"send_email","status":"PENDING","payload":{"to":"user@example.com","subject":"Test","body":"Hello"}}]
  ```
- Navigate to `/dashboard/ai`, send a message
- Assert: HITL approval UI is visible (look for approve/reject buttons or the action card)

**FALLBACK for Test 3:** If the HITL card depends on the poll-based `useAiActions` hook, the mock must return data on the pending actions endpoint. If the exact mechanism is unclear, use a simpler assertion: verify the chat response renders and check for the presence of any approval-related UI element. Mark with a TODO comment if the exact HITL E2E flow needs refinement.

**Test 4: "briefing widget renders on dashboard"**
- Mock `GET **/api/v1/ai/briefing` (or whatever endpoint the DailyBriefing widget uses) with a canned briefing response
- Navigate to `/dashboard` (main dashboard, not /dashboard/ai)
- Assert: briefing card/widget is visible (look for a heading or text content that matches the briefing)

**Test 5: "mobile chat layout at 375px"**
- Set viewport to 375x812 (iPhone X dimensions)
- Navigate to `/dashboard/ai`
- Assert: The chat thread area is visible (full-screen on mobile)
- Assert: The sidebar/conversation list is NOT visible by default (hidden on mobile, shown via hamburger toggle)
- If there's a hamburger/menu button, click it and assert the sidebar becomes visible

**Route interception pattern:**
```typescript
await page.route('**/api/v1/ai/chat', async (route) => {
  const body = '0:"Hello from the AI assistant!"\n' +
    'd:{"finishReason":"stop","usage":{"inputTokens":10,"outputTokens":5}}\n';
  await route.fulfill({
    status: 200,
    contentType: 'text/plain; charset=utf-8',
    body,
  });
});
```

**IMPORTANT:** If the Data Stream format mock codes (`0:`, `9:`, `a:`, `d:`) don't work (assistant-ui doesn't parse them correctly), fall back to observing a real response format first:
1. Start the backend locally
2. Use Playwright's `page.on('response')` to capture the actual response body from a real chat request
3. Use that exact format in the mocks
