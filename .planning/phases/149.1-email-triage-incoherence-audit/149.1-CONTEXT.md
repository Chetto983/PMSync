# Phase 149.1 - Email Triage Incoherence Audit (CONTEXT)

## Why this phase exists

The current v13 triage stack is no longer a single classifier. It now spans:

- classification and persistence (`EmailAnalysisService`, `EmailTriageService`)
- override and correction logic (`TriageOverrideService`, `TriageCorrectionService`)
- follow-up creation and backfill (`TriageActionService`, `FollowUpDetectionService`)
- downstream consumers (`DashboardTodayService`, task aggregation, triage UI)

The user reported that "email triage is too stupid" and asked for a deep audit of incoherence. The goal of this phase is to explain where that feeling comes from, prove the failures with local evidence, and leave behind implementation-ready documents for the actual fix work.

This phase is documentation-first. It does not change APIs, DTOs, Prisma schema, or triage behavior.

## Audit boundary

### In scope

- backend classification and persistence
- override and correction logic
- follow-up/reminder creation
- learning, recalculation, and backfill seams
- dashboard/task/frontend surfaces that consume triage output
- planning/documentation drift that can mislead future triage work
- targeted local test execution and dev-oriented repro commands

### Out of scope

- production mutation or live-data fixes
- code fixes for confirmed defects
- schema changes
- broad full-suite validation
- Phase 149 temporal decay implementation itself

## Locked decisions

### D-01: Treat this as a parallel v13 phase

This phase is inserted as `149.1`, parallel to Phase 149, not a blocker gate. Findings should inform Phases 150-156 and any dedicated bug-fix phase opened afterward.

### D-02: Evidence standard is code + targeted tests + dev repro

Each finding must be supported by one or more of:

- direct code inspection
- targeted spec result
- concrete local repro command

No production mutation is allowed for this phase.

### D-03: Confirmed defects and guarded seams are both valid outputs

The audit distinguishes:

- confirmed defects
- documentation/process drift
- guarded seams that are currently protected by tests but remain high-risk duplicate-source paths

### D-04: Narrow test entrypoints are the default workflow

The useful audit entrypoints are narrow direct Jest invocations, not full backend test runs:

- `triage-action.service.spec.ts`
- `email-triage.service.spec.ts`
- `follow-up-detection.service.spec.ts`
- `dashboard-today.service.spec.ts`
