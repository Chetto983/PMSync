## Confirmed Findings

### F-01 - Passive notification suppression is missing in `TriageActionService`

**Subsystem:** follow-up/reminder creation  
**Severity:** High  
**Incoherence class:** code vs test drift, split semantics between classifier and action layer

**Expected behavior**

Passive notifications should not create follow-ups, even if upstream model output is noisy. This is asserted explicitly by:

- `backend/src/modules/ai/services/__tests__/triage-action.service.spec.ts:101`
- prompt guidance in `backend/src/modules/ai/locales/en.ts:214-215`

**Actual behavior**

`TriageActionService.processTriageSignals()` only checks `hasDeadline`, `actionability`, and `needsFollowUp`. There is no passive-notification suppression branch in:

- `backend/src/modules/ai/services/triage-action.service.ts:59`
- `backend/src/modules/ai/services/triage-action.service.ts:216`

The targeted spec fails:

- `backend/src/modules/ai/services/__tests__/triage-action.service.spec.ts:101`
- failure observed on 2026-04-23: expected `followUpCreated=false`, received `true`

**Evidence**

- Failing spec: `triage-action.service.spec.ts`
- Contrasting positive case still passes:
  `backend/src/modules/ai/services/__tests__/triage-action.service.spec.ts:166`
- Upstream classifier guidance already treats passive notifications as non-follow-up by default:
  `backend/src/modules/ai/locales/en.ts:214-215`

**Reproduction**

1. Run:
   ```powershell
   node -r dotenv/config .\node_modules\jest\bin\jest.js src/modules/ai/services/__tests__/triage-action.service.spec.ts --runInBand
   ```
2. Observe the failure on `should skip passive notifications even if the model flagged follow-up`.

**User-visible impact**

- false-positive follow-ups for GitHub/Vercel/Railway-style notifications
- noisy follow-up indicators in email UI
- unnecessary follow-up/task pressure in downstream surfaces
- degraded trust in triage because "routine updates" look actionable

**Recommended fix stream**

- `Stream A - classifier semantics`
- `Stream B - follow-up suppression and actionability rules`

**Subsystem:** dashboard/task aggregation  
**Current state:** guarded seam, not failing

- unified task results
- raw `EmailFollowUp` records

- `backend/src/modules/dashboard/services/dashboard-today.service.ts:190-198`

The protection is real and tested:

- `backend/src/modules/dashboard/services/__tests__/dashboard-today.service.spec.ts:238-285`
- targeted spec result on 2026-04-23: **PASS 17/17**

**Why it matters**

This is still a duplicate-source path. Any future change to either task normalization or follow-up aggregation can reintroduce double-counting.

**Recommended fix stream**

- `Stream C - downstream aggregation and source-of-truth cleanup`

### G-02 - `EmailFollowUp` has two writers by design: live triage and backfill detection

**Subsystem:** follow-up persistence  
**Current state:** guarded seam, not failing

Two producers exist:

- live path: `TriageActionService`
- backfill path: `FollowUpDetectionService`

The backfill path explicitly avoids overlap via:

- `backend/src/modules/ai/services/follow-up-detection.service.ts:181-189`

The targeted spec for that filtering currently passes:

- `follow-up-detection.service.spec.ts` -> **PASS 8/8**

**Why it matters**

The architecture is coherent today only because the second writer is carefully fenced. If those fences drift, duplicate follow-ups or conflicting reasons/dates can appear.

**Recommended fix stream**

- `Stream B - follow-up suppression and actionability rules`
- `Stream C - downstream aggregation and source-of-truth cleanup`
