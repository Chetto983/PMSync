# Phase 149.1 - Improvement Spec

## Purpose

This document groups the audit findings into implementation streams so a follow-up fix phase can execute without re-deciding scope.

It is not the fix phase itself.

## Stream A - Classifier semantics

### Goal

Make passive-notification suppression a single explicit invariant, not an emergent side effect of prompts plus downstream heuristics.

### Required outcomes

- passive notifications default to non-follow-up
- actionable incidents and real deadlines still break through
- the invariant is enforced in a place future contributors will actually hit

### Implementation direction

- define one authoritative suppression rule for passive notifications
- either:
  - centralize it in a shared helper used by both classification and follow-up action code, or
  - make `UnifiedEmailAnalysis` carry a stronger explicit suppression signal that `TriageActionService` must obey
- remove any reliance on prompt wording alone as the only protection

### Acceptance

- the current failing `triage-action.service.spec.ts` passive-notification case passes
- the actionable update positive case still passes

## Stream B - Follow-up suppression and actionability rules

### Goal

Make `EmailFollowUp` creation rules consistent across live triage, overrides, and backfill detection.

### Required outcomes

- `TriageActionService` and `FollowUpDetectionService` no longer drift semantically
- `never-follow-up` remains authoritative
- passive notifications, FYI digests, and routine alerts do not create false-positive follow-ups

### Implementation direction

- review `processTriageSignals()` and `shouldCreateFollowUp()`
- define explicit precedence:
  1. muting override / suppression signal
  2. real deadline
  3. explicit actionability
  4. fallback `needsFollowUp`
- keep backfill path fenced to un-triaged + no-existing-follow-up records
- add regression tests for passive notification, actionable alert, waiting-for, and todo classification

### Acceptance

- no duplicate `EmailFollowUp` creation path for the same scenario
- no passive-notification false positives
- waiting-for vs todo behavior remains covered by tests

## Stream C - Downstream aggregation and source-of-truth cleanup

### Goal

Reduce incoherence in places where triage output becomes visible to the user.

### Required outcomes

- one clear source of truth for follow-up work per surface
- dashboard, task aggregation, and triage UI do not double-count or conflict
- duplicate-source seams remain explicit and tested if they cannot yet be removed

### Implementation direction

- review whether dashboard should continue merging both task-normalized follow-ups and raw `EmailFollowUp`
- decide if one source should become canonical for Today feed
- document or refactor the relationship between:
  - `DashboardTodayService`
  - task aggregation normalizers
  - email follow-up UI indicator

### Acceptance

- dashboard dedup remains green or becomes unnecessary because only one source is used
- no change reintroduces duplicate follow-up items for a single email

## Stream D - Test harness and env cleanup

### Goal

Make narrow triage debugging fast and repeatable on local Windows shells.

### Required outcomes

- a documented narrow-test command works without shell-specific guesswork
- engineers do not need to rediscover the direct Jest entrypoint during triage debugging

### Implementation direction

- either fix the npm wrapper path for targeted runs on Windows, or
- formally document and script the direct Node + Jest path as the supported narrow-debug entrypoint
- avoid requiring full-suite runs for triage repro

### Acceptance

- one documented command runs `triage-action.service.spec.ts` reliably from `backend/`

## Stream E - Docs and roadmap reconciliation

### Goal

Bring triage docs and milestone artifacts back in sync with live implementation.

### Required outcomes

- stale architecture claims are corrected
- roadmap/state disagreement is removed
- future triage phases do not start from false assumptions

### Implementation direction

- update `docs/TRIAGE_FOLLOWUP_REMINDER_CONSOLIDATION.md` to reflect the live architecture
- reconcile `.planning/ROADMAP.md` and `.planning/STATE.md` for Phase 148 status
- treat triage docs as part of runtime safety because they drive future agent behavior

### Acceptance

- no triage architecture doc claims follow-ups are unimplemented when code says otherwise
- milestone status for shipped triage work is consistent across planning artifacts

## Suggested follow-up phase split

If this becomes executable work, split it in this order:

1. Fix the passive-notification suppression defect.
2. Reconcile follow-up creation semantics across live and backfill writers.
3. Clean up downstream source-of-truth seams.
4. Normalize test entrypoints and docs.
5. Re-run the same narrow evidence suite used in 149.1.
