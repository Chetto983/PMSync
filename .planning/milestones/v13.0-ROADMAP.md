# Roadmap: PMSync v13.0 — Intelligent Triage & Memory Consolidation

## Overview

Transform email triage from a stateless LLM classifier into a learning system that improves from user corrections via graph-based memory consolidation, per-label accuracy tracking, and OpenClaw-inspired dreaming phases. Harden label creation with semantic overlap detection, conflict enforcement, and safety governance to prevent memory poisoning and semantic drift.

**Research basis:** OpenClaw Dreaming System (3-phase consolidation), Graphiti/Zep (temporal knowledge graphs), SSGM (arXiv:2603.11768, safety governance), Trainable Graph Memory (arXiv:2511.07800), Mem0 (importance scoring), RLM (batch reclassification pattern).

## Phase Details

### Phase 147: Close the Feedback Loop
**Goal**: Wire existing triage corrections from `TriageFeedbackService` back into the triage pipeline so future classifications benefit from past corrections
**Depends on**: None (foundation)
**Requirements**: LEARN-01, LEARN-02
**Success Criteria** (what must be TRUE):
  1. When a user corrects a label assignment, the next triage of an email from the same sender uses that correction as a hint
  2. `TriageFeedbackService.getSuggestions()` output auto-creates `TriageOverride` entries when correction confidence exceeds 80%
  3. Few-shot correction examples injected into LLM prompt for sender/domain matches
**Plans**: 5 plans (01-schema+helpers, 02-BLOCKING-migration, 03-promotion+prompt+queue, 04-consumers, 05-admin+integration-test)
**UI hint**: no

### Phase 149: Temporal Memory Decay
**Goal**: Replace flat 30-day TTL in `TriageLearningService` with exponential decay (14-day half-life) so recent corrections carry more weight than stale ones
**Depends on**: Phase 147
**Requirements**: LEARN-04
**Success Criteria** (what must be TRUE):
  1. EMA sender scores use configurable half-life decay (default 14 days, env `TRIAGE_DECAY_HALF_LIFE_DAYS`)
  2. Correction weight computed as `e^(-lambda * days_since_correction)` where lambda = ln(2)/14
  3. Patterns with decayed confidence below 0.3 are garbage-collected by nightly job
  4. Nightly recalculation uses temporal weights, not raw counts

**UI hint**: no

### Phase 150: Graph-Based Triage Memory
**Goal**: Extend `EntityGraphService` with sender-to-label and domain-to-label edges carrying confidence scores and temporal validity, then wire into triage scoring
**Depends on**: Phase 148, Phase 149
**Requirements**: GRAPH-01, GRAPH-02, GRAPH-03
**Success Criteria** (what must be TRUE):
  1. New edge types: `SENDER_LABEL_AFFINITY`, `DOMAIN_LABEL_AFFINITY` on `GraphEdge` with `confidence` (Float), `validFrom` (DateTime), `validUntil` (DateTime?)
  2. Triage pipeline queries graph before LLM: confidence >= 0.9 skips LLM call, 0.7-0.9 uses as hint in prompt
  3. Graph edges created/updated only by consolidation loop (not inline during triage)
  4. Measured LLM call reduction >= 20% on repeat senders after 30-day warmup

### Phase 151: Dreaming Consolidation Loop
**Goal**: Implement OpenClaw-inspired 3-phase memory consolidation (Light/Deep/REM) as BullMQ cron jobs that compress, promote, and discover patterns from triage corrections
**Depends on**: Phase 150
**Requirements**: DREAM-01, DREAM-02, DREAM-03
**Success Criteria** (what must be TRUE):
  1. Light phase (hourly): merges correction buffer entries for same sender+label, updates EMA scores, deduplicates (cosine similarity > 0.9)
  2. Deep phase (nightly 3AM): promotes patterns with >= 3 corrections and confidence > 0.8 to graph edges with temporal validity, recalculates per-label accuracy, applies temporal decay
  3. REM phase (weekly Sunday 5AM): cross-label contradiction detection, domain-level pattern aggregation (sender patterns rolled up to domain), stale edge cleanup (confidence < 0.3)
  4. All phases are BullMQ repeatable jobs with Redis single-instance locks (consistent with v11.0 pattern)
  5. Each phase emits Prometheus metrics: `triage_patterns_promoted_total`, `triage_edges_decayed_total`, `triage_contradictions_found_total`
**Plans**: 6 plans

### Phase 152: Triage Safety Governance
**Goal**: Prevent memory poisoning, semantic drift, and stale retrieval in the consolidation loop via SSGM-inspired safety gates
**Depends on**: Phase 151
**Requirements**: SAFE-01, SAFE-02, SAFE-03
**Success Criteria** (what must be TRUE):
  1. Minimum 3 corrections required before any pattern promotion (anti-poisoning threshold)
  2. Max 10 pattern promotions per nightly Deep cycle (rate limiting)
  3. Contradiction gate: new pattern contradicting existing high-confidence (> 0.8) pattern flagged for human review, not auto-applied
  4. Auto-rollback: if per-label accuracy drops > 15% after consolidation cycle, revert that cycle's graph mutations
  5. Audit log: every consolidation action (promote, decay, delete, revert) logged to `TriageConsolidationAudit` table with before/after state
**Plans**: TBD
**UI hint**: no

### Phase 153: Label Creation Hardening
**Goal**: Harden the label wizard with semantic overlap detection, duplicate prevention, aiPrompt quality validation, and bidirectional mutuallyExclusiveWith enforcement
**Depends on**: Phase 148
**Requirements**: LABEL-01, LABEL-02, LABEL-03
**Success Criteria** (what must be TRUE):
  1. Wizard warns when new label's aiPrompt has > 80% semantic overlap with existing label (cosine similarity on embeddings)
  2. `mutuallyExclusiveWith` validated bidirectionally on create/update (if A excludes B, B must exclude A)
  3. aiPrompt quality score (length >= 20 chars, has action verb, has specificity keywords) shown during wizard with pass/warn/fail badge
  4. Duplicate slug detection prevents near-identical labels (Levenshtein distance < 3)
  5. Label merge tool: combine two labels into one, re-assign all EmailLabel records, trigger batch re-triage of affected emails
**Plans**: TBD
**UI hint**: yes

### Phase 154: Batch Reclassification Engine
**Goal**: When a user modifies a label's aiPrompt or creates a new label with backfill, automatically re-classify affected emails using partition+map+aggregate (inspired by RLM context decomposition)
**Depends on**: Phase 150
**Requirements**: BATCH-01, BATCH-02
**Success Criteria** (what must be TRUE):
  1. Label aiPrompt change triggers BullMQ job to re-triage emails previously assigned that label (last 30 days)
  2. New label creation offers "backfill" toggle to scan recent emails (last 7 days)
  3. Batch jobs partition emails into chunks of 20, process as parallel BullMQ sub-jobs, aggregate results
  4. Progress shown via WebSocket notification in frontend (X of Y emails re-classified)
  5. Re-classification respects existing user overrides (never re-triage overridden emails)
**Plans**: TBD
**UI hint**: yes (backfill toggle, progress notification)

## Requirements

### LEARN — Learning from Corrections
- **LEARN-01**: Triage corrections feed back into future triage decisions for same sender/domain
- **LEARN-02**: Auto-create TriageOverride entries when correction confidence exceeds 80%
- **LEARN-03**: Per-label precision and recall tracked and exposed via API
- **LEARN-04**: Temporal decay (14-day half-life) replaces flat 30-day TTL on learned patterns

### GRAPH — Graph-Based Memory
- **GRAPH-01**: Sender-to-label and domain-to-label graph edges with confidence scores
- **GRAPH-02**: Confidence gating: skip LLM for high-confidence patterns (>= 0.9)
- **GRAPH-03**: Graph edges carry temporal validity windows (validFrom/validUntil)

### DREAM — Dreaming Consolidation
- **DREAM-01**: Light consolidation: hourly compression, EMA update, deduplication
- **DREAM-02**: Deep consolidation: nightly pattern promotion, accuracy recalculation, temporal decay
- **DREAM-03**: REM consolidation: weekly contradiction detection, domain aggregation, stale cleanup

### SAFE — Safety Governance
- **SAFE-01**: Anti-poisoning: minimum 3 corrections before pattern promotion
- **SAFE-02**: Contradiction gate: conflicting patterns require human review
- **SAFE-03**: Auto-rollback on accuracy regression (> 15% drop)

### LABEL — Label Hardening
- **LABEL-01**: Semantic overlap detection on label creation (> 80% cosine similarity)
- **LABEL-02**: Bidirectional mutuallyExclusiveWith enforcement
- **LABEL-03**: Label merge tool with re-triage of affected emails

### BATCH — Batch Reclassification
- **BATCH-01**: Batch re-triage triggered on aiPrompt change (last 30 days)
- **BATCH-02**: New label backfill option (last 7 days)

### OBS — Observability
- **OBS-01**: Per-label accuracy API endpoint
- **OBS-02**: Triage observability dashboard with accuracy charts and consolidation health
- **OBS-03**: LLM call savings metrics (graph vs LLM classification ratio)

### VAL — Validation
- **VAL-01**: Before/after accuracy benchmark script
- **VAL-02**: Prometheus alerting on sustained accuracy regression

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| Build on existing EntityGraphService, not adopt Graphiti/Mem0 | PMSync already has GraphNode/GraphEdge + recursive CTE (60% of Graphiti); adding Neo4j dependency is overkill for a solo-dev project |
| BullMQ crons for dreaming phases | Consistent with v11.0 decision: single-instance via Redis locks, no @Cron |
| Confidence gating to skip LLM | Cost reduction: high-confidence graph patterns (>= 0.9) don't need LLM confirmation |
| Min 3 corrections before promotion | SSGM anti-poisoning: single corrections could be user mistakes |
| 14-day half-life exponential decay | Matches OpenClaw Deep Dreaming recency half-life; better than flat 30-day TTL |
| Per-label accuracy in Postgres | Need historical trends for dashboard charts, not just current state |
| Partition+map for batch reclass | RLM-inspired: chunks of 20 emails avoid context rot in LLM batch calls |
| Contradiction gate with human review | SSGM: auto-applying contradictory patterns causes oscillation; human breaks the tie |
