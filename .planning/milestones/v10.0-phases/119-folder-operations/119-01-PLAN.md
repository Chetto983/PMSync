Create `scripts/lib/validate-folder-ops.mjs` following the `validate-drafts-bulk.mjs` pattern. Export a single `validateFolderOps(context, cookieHeader, csrfToken, options)` function that returns a results array.

**Helpers** (copy pattern from validate-drafts-bulk.mjs):
- `getProviders(context, cookieHeader)` -- GET /api/v1/providers, return array
- `providerTypeLabel(provider)` -- map google->Gmail, microsoft->Outlook, imap->IMAP
- `matchesProviderFilter(provider, filter)` -- match CLI filter to provider type
- `getFolders(context, cookieHeader, providerId)` -- GET /api/v1/folders/provider/:providerId, return array
- `sleep(ms)` -- simple promise-based delay for queue processing

**Main function `validateFolderOps`:**

1. Call `setResultsCollector(results)` with fresh results array
2. Fetch providers via `getProviders()`, filter by `options.provider`
3. For each matching provider, run the test sequence below
4. After all provider tests, run system folder protection tests (FOLD-05)
5. Return results array

**Per-provider test sequence** (use unique timestamp suffix `Date.now()` in folder names):

**FOLD-01 -- Create folder:**
- POST /api/v1/folders with body `{ name: "Test-Fold-{timestamp}", providerId: provider.id }`
- Wait 3 seconds for BullMQ queue processing
- GET /api/v1/folders/provider/:providerId
- `assertTrue("[providerLabel] FOLD-01: Create folder returns success", response status is 200 or 201, results)`
- `assertTrue("[providerLabel] FOLD-01: Created folder appears in list", folders.some(f => f.name includes "Test-Fold-{timestamp}"), results)`
- Save the created folder's ID for rename/delete tests

**FOLD-02 -- Rename folder:**
- PATCH /api/v1/folders/:folderId with body `{ newName: "Renamed-{timestamp}" }`
- Wait 3 seconds for queue processing
- GET /api/v1/folders/provider/:providerId
- `assertTrue("[providerLabel] FOLD-02: Rename returns success", response is 200, results)`
- `assertTrue("[providerLabel] FOLD-02: Renamed folder name updated in list", folders.some(f => f.name includes "Renamed-{timestamp}"), results)`

**FOLD-03 -- Delete folder:**
- DELETE /api/v1/folders/:folderId
- Wait 3 seconds for queue processing
- GET /api/v1/folders/provider/:providerId
- `assertTrue("[providerLabel] FOLD-03: Delete returns success", response is 200, results)`
- `assertTrue("[providerLabel] FOLD-03: Deleted folder gone from list", !folders.some(f => f.id === folderId), results)`

**FOLD-04 -- Sync from provider:**
- POST /api/v1/folders/sync/:providerId
- `assertTrue("[providerLabel] FOLD-04: Sync returns success", response is 200 or 201, results)`
- GET /api/v1/folders/provider/:providerId
- `assertTrue("[providerLabel] FOLD-04: Folders exist after sync", folders.length > 0, results)`
- Note: Full external-change detection requires creating a folder externally which cannot be automated. The sync endpoint itself being callable and returning data is the automated check. The human checkpoint in Plan 02 covers the full external-change scenario.

**FOLD-05 -- System folder protection (once, using first available provider):**
- GET /api/v1/folders/provider/:providerId for the first provider
- Find a system folder: look for `specialUse` in ['INBOX', 'SENT', 'TRASH', 'DRAFTS'] or name matching those
- If found:
  - DELETE /api/v1/folders/:systemFolderId -- expect 400 or 403 response
  - `assertTrue("FOLD-05: Delete system folder blocked", response status is 400 or 403, results)`
  - PATCH /api/v1/folders/:systemFolderId with body `{ newName: "hacked" }` -- expect 400 or 403
  - `assertTrue("FOLD-05: Rename system folder blocked", response status is 400 or 403, results)`
- If not found: `assertTrue("FOLD-05: System folder found for testing", false, results)` -- flag as failure

**Error handling:** Wrap each provider's test sequence in try/catch. On error, push a FAIL result with the error message and continue to next provider.

**Important implementation details:**
- API calls may return the result in different envelope shapes. Use defensive unwrapping: `res?.data ?? res` for folder arrays
- The create/rename/delete endpoints queue BullMQ jobs and poll for completion (30s server-side timeout), so the 3-second client-side wait is a safety margin, not the primary wait
- For FOLD-05, the controller should return 400 with an error message containing "system" or "cannot" -- validate the status code, not the message body
