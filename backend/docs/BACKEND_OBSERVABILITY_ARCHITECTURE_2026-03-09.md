# Backend Observability Architecture

Date: 2026-03-09
Scope: Current backend monitoring, logging, metrics, health, and operational exposure
Status: Current reference

## Summary

The backend has a meaningful observability foundation:

- structured logging with `nestjs-pino`
- request IDs and correlation context
- Prometheus metrics at `/metrics`
- queue metrics collection
- AI run ledger telemetry
- health and queue inspection endpoints

This is a solid baseline for a monolith, but the current operational exposure is too open and the monitoring configuration still points at deprecated endpoints.

## Logging

Current logging baseline:

- `nestjs-pino` is the primary logger
- request IDs are accepted or generated by middleware
- correlation IDs are propagated through request context
- logs include request and correlation context for tracing across async flows

This is one of the stronger operational parts of the current backend.

## Metrics

### Prometheus Endpoint

The canonical metrics endpoint is:

- `/metrics`

It is provided by the global `MetricsModule` through `@willsoto/nestjs-prometheus`.

Current built-in metric categories:

- default Node.js metrics
- HTTP request duration histogram
- in-flight HTTP request gauge
- BullMQ queue depth gauge
- AI token counter
- AI cost counter
- AI request counter

### Queue Metrics

Queue depth metrics are collected on a schedule and exported to Prometheus.

There is also a separate queue health service that can expose queue state in JSON and legacy Prometheus-text form.

### AI Observability

The backend also tracks AI usage through the run ledger.

This gives the platform more than just infrastructure metrics:

- run counts
- token consumption
- estimated cost
- tenant- and user-linked AI activity

## Health Endpoints

The `HealthController` exposes:

- `/health`
- `/health/ready`
- `/health/live`
- `/health/queues`
- `/health/queues/all`
- `/health/queues/:name`
- `/health/metrics`

Important current behavior:

- the entire health controller is `@Public()`
- queue details are therefore available without authentication
- `/health/metrics` is explicitly deprecated in favor of `/metrics`

This is operationally convenient for local development, but too broad for a hardened production posture.

## Monitoring Configuration Drift

The repo monitoring configuration still scrapes:

- `/health/metrics`

instead of:

- `/metrics`

That means the monitoring setup is currently aligned to the deprecated path rather than the canonical metrics endpoint.

## Realtime and Queue Visibility

The backend includes infrastructure that helps with operational debugging:

- Redis-backed Socket.IO adapter
- BullMQ queue services and workers
- queue health inspection
- queue depth metrics
- dead-letter queue support

This is useful for diagnosing background processing and realtime delivery problems.

## Strong Points

### Correlation Infrastructure

Request IDs and correlation context are present and used across HTTP and some async operations.

### Prometheus Foundation

There is a real metrics module, not just hand-built text output.

### AI Telemetry

The run ledger means AI activity is observable at the application layer, not only at the infrastructure layer.

### Queue Visibility

BullMQ health, depth, and status reporting are better than average for a mid-stage SaaS backend.

## Current Gaps

### Public Operational Exposure

The current public health controller exposes more operational detail than it should.

Examples:

- queue inventory and state
- deprecated metrics text endpoint

### Deprecated Metrics Path Still in Use

Prometheus is configured against `/health/metrics`, even though the codebase now treats `/metrics` as the canonical endpoint.

### No Distributed Tracing Stack

The backend has correlation IDs, but I did not find full OpenTelemetry or equivalent distributed tracing infrastructure in the active stack.

### Mixed Metrics Surfaces

There are two operational metrics styles in play:

- canonical `/metrics` via Prometheus module
- legacy hand-built text from queue health under `/health/metrics`

This should be collapsed to one source of truth.

## Guidance for Contributors

1. Treat `/metrics` as the canonical Prometheus endpoint.
2. Do not add new monitoring integrations against `/health/metrics`.
3. Keep request/correlation IDs flowing through new async and queue code.
4. Avoid exposing queue or internal operational state on public unauthenticated endpoints in production-facing designs.
5. Prefer extending the metrics module and run ledger over inventing separate observability silos.

## Recommended Next Hardening Steps

1. Move Prometheus scraping from `/health/metrics` to `/metrics`.
2. Restrict detailed health and queue endpoints to internal access or authenticated admin access.
3. Remove the deprecated metrics text path after monitoring has migrated.
4. Expand AI observability to cover tool calls, approval flow outcomes, and blocked actions more accurately.
5. Add tracing if the system continues growing in queue and realtime complexity.

## Current Assessment

Observability maturity: good foundation, incomplete hardening.

The backend is strongest in structured logs, metrics foundation, and queue visibility, and weakest in exposure discipline and convergence on a single monitoring path.
